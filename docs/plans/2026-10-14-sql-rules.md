# 规则库改造为「SQL 规则」（特殊 Skill）

## 背景

原规则库有「内置规则 + 项目自定义规则」，规则分 `sql` / `prompt` 两类，支持试跑与批量运行
（批量运行会把命中行写成审计疑点）。用户决定：

- **Skills 与规则都不内置**，全部由用户自己添加。
- 规则模块**只保留 SQL**：用户保存自定义 SQL，并配一段自然语言**描述**。
- **试跑**需要**选择数据库**；**只回显结果**，是否记疑点交给模型判断（去掉 severity）。
- **模型能感知这些 SQL 并运行** —— 「总结就是一个特殊一些的 skill」。
- 移除「批量运行」。

## 设计（B2 方案）

### 数据模型 `AuditRule`（项目级，`.fireeye/rules.jsonl`）

```ts
{ id, name, description, sql, enabled, databaseId? }
```

- 移除 `builtin` / `type` / `detector` / `severity` / `params` / `scope` / `nameKey` / `descriptionKey`。
- `databaseId`：可选**默认数据库连接 id**；缺省在工作区 DuckDB 上运行。

### 感知：注入系统提示词

`agent/graph.py` 把所有**启用**规则渲染进 system prompt，`agent/prompts.py` 输出：

```
已知的自定义审计查询（用 run_rule 运行；不确定数据源时先 describe_source）：
- [R-0001] 余额非零
  说明：检查科目余额是否非零，发现挂账
  SQL: SELECT ...
  默认数据库：conn_x
```

### 使用：新增 `run_rule` 工具

模型调 `run_rule(ruleId, sourceId?)`，后端按 id 取出 SQL 执行并返回行结果。

- `sourceId` 缺省用规则的 `databaseId`，可临时覆盖 → 解决「规则不绑定库」的歧义。
- 结果天然关联 `ruleId`，模型记疑点时 `ruleKey` 干净。
- SQL 仍注入 prompt，所以模型照样「感知到这些 SQL」。
- 会话上下文（允许的连接）仍生效（`allowedConnectionIds`）。

### 后端

- `store/rules.py`：删除内置与合并逻辑，事件字段改 `name/description/sql/databaseId/enabled`。
- `store/rule_engine.py`：`run_rule(root, id, source_id=None, allowed_connection_ids=None)` 复用
  `sql_query` 返回结果；删除 detector 与 `run_all_rules`。
- `api/rules.py`：Body/Patch 改字段；`POST /rules/{id}/run?sourceId=`；删除 `POST /rules/run`。
- `tools/run_rule.py` + `tools/registry.py`：注册 `run_rule`，上下文包装注入 `allowedConnectionIds`。

### 前端

- `RulesPanel`：顶部「试跑数据库」下拉（规则默认 / 工作区数据 / 各连接）+「新增规则」；单列表；
  卡片显示 名称 / 描述 / SQL；`试跑`（就地显示结果表）/ 编辑 / 删除 / 启用。移除内置分区与批量运行。
- `RuleForm`：名称、描述、SQL、默认数据库、启用。
- `Skill` 类型去掉 `builtin`，`scope` 收敛为 `ConfigScope`；`SkillsPanel`/`SkillForm` 去掉内置徽章与分支。

### 清理

- i18n：`skills.builtin`；`rules.builtin/custom/type*/definition/severity/runAll/builtinRules`；
  `error.ruleNotRunnable/skillBuiltin`。
- 测试：`test_rules_store/api/rule_engine`、`test_skills_store/api`、`test_prompt_rules`、
  `test_tool_registry` 同步更新。
